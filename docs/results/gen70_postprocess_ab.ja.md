# gen70 の後処理 A/B 結果(2026-10-17)

最終提出 sub125 / sub126 の方策 gen70 に、gen41(`gen41_postproc_20261001`)と同じ同一局比較を掛けた結果。

## 条件

- **相手と局数:** 7 本(sub121_v109、sub122_v4x20、sub123s_gen21、mmpqbcw_gen32、mmpqbcw_gen34、mmpqbcw_gen35、sub124)。seed は 174300000〜174300127(128 個)で、両 player を打つ。1 腕 1,792 局で、腕どうしは同じ局(相手・seed・player が同じ)を比べる。
- **エンジン:** Rust の高速エンジン。公式エンジンと遷移ごとに一致することは既存の検証で確認済みで、本実験では再検証していない。
- **相手の性質:** 相手はすべて本チームの提出物で、盤面に反応して手を変える。固定の行動列を再生しているわけではない。そのため腕によって相手の手も変わる。
- **学習側:** gen70(sub125 の `policy.pt`)+ gen41 の main.py。fp32、TF32 は無効。
- **腕の中身:**
  - A: 網 → `_pace` → `_land`(後処理なし)
  - C: A + 無駄手の修正(W3+W5+W6+W9'+WT)・溢れと最終手の売り + 最終日の回収計画(708、α=0.01)
  - B: C + hour 23 の倉庫売り(D23S_p1)
  - D: B + MELON16(= sub125 の agent())
  - E: D + メロンの植え直し(= sub126 の agent())
- **勝率の数え方:** 分けは 0.5 として数える。区間は seed を単位にした bootstrap(10,000 回)の 95% 区間。符号検定は、結果が変わった局(分けを含む改善と悪化)の数で行う。

## smoke の照合(parity)の問題と修正

- **smoke try 1(19:24〜19:29):**
  - integrity D_vs_A の不一致は 0 / 32。
  - parity_submission(提出物の agent() との全手照合)は、A・D とも 2 / 2,876 手で不一致だった。
  - 不一致の箇所は sub124 / seed 174300001 / 両 player / step 228 / hands[9]。harness は `PLACE GOOSE 1`、照合側は `PLANT WHEAT`。
- **原因(照合側):**
  - `submission_agent()` は `sys.modules` から後処理 5 本しか外していなかった。そのため sub125 の main.py が、先に読み込まれていた masspeaks の BC kit の原本(original)の `obs_feat.py` を使っていた。この版には nmb の印がない。
  - その結果、legal が 1 局あたり 415 マスで「kit 版 0 / sub125 版 3」と食い違った。unit 10 の PLACE GOOSE も kit 版では非合法になる。
  - `model_tf.py` は sha が同一なので影響はない。
- **harness が正しいことの確認:**
  - harness の網への入力(Rust の特徴 + nmb の印)は、sub125 の obs_feat と完全に一致した(tiles / ou / pu / g / legal の最大差 0)。
  - unit logits の CPU / GPU の差は最大 1.5e-5(相対 1.6e-5)。
  - unit 10 の上位 3 手は、CPU も GPU も PLANT TOMATO 25.0366(p=0.998)、PLACE GOOSE 18.1145、PLANT WHEAT 17.2953。PLACE GOOSE と PLANT WHEAT の差は 0.819 で、拮抗していない。
  - トマトの種(在庫 1)は unit 7 が既に使っているので、正しく貪欲に選ぶと PLACE GOOSE になる。harness はそれを出している。
  - 根拠: `diag/diag_step228.json`、`diag/diag_legal.json`。diag_step228.json の `cpu_agent` は「sub125 の obs_feat で計算した CPU の logits」のこと。
- **修正:**
  - `run_gen70.py` の `submission_agent()` だけを直した。`obs_feat` / `model_tf` / `model_ptr_infer` も外し、提出物のフォルダを `sys.path` の先頭に置いて読み、読んだ module の `__file__` を assert する。
  - 対局の経路は変えていない。
  - sha は 4a22ef3d… → 1225cd7a…。protocol.json と README の変更履歴に記録した。
- **smoke try 2(20:43〜20:48):**

  | 項目 | try 1 | try 2 |
  |---|---|---|
  | integrity D_vs_A の不一致 | 0 / 32 | 0 / 32 |
  | parity A の不一致 | 2 / 2,876 | 0 / 2,876 |
  | parity D の不一致 | 2 / 2,876 | 0 / 2,876 |
  | 成績(32 局) | A 13-0-19 / D 21-0-11 | 同じ |

## 出来事

1. smoke try 1 の parity 不一致について、原因を診断し、照合側を直して smoke をやり直した(前節)。
2. 腕 A の途中(21:02:16〜21:04:00)、GPU メモリが当時の停止基準 80% を超え、最大 20,431 MiB(83%)になった。
   - 電力は 330〜337 W のままで、メモリ詰まりは起きていない。
   - 管理側はその時点で別の待機コマンドで止まっていて、すぐには止められなかった。A は 11/11 で完走した。
   - 21:09:30 に、起動 27 秒後の腕 C(対局開始前)とランチャーを PID 指定で停止し、報告した。
3. 21:15:49 に、80% の基準を取り下げて再開した(同じ設定で C → B → D → E)。腕 C の旧ログは `killed_C_try1_logs/` に移した。
4. 21:17:09 に方針が変わり、メモリは停止理由にしないことになった。
   - 腕 C は 11 並列のまま最後まで走らせた。そのためにランチャー 2 だけを止めている。C の part は止めていない。
   - B・D・E は `launcher3.sh` で走らせた。job の割り方は同じ(`part <腕> <k> 11`、PLAN_PROCS=2)で、同時に走る part を最大 9 本にする待ち行列にした。
   - 22,100 MiB 超えか電力の急落があれば並列数を 1 ずつ下げる設定にしたが、一度も発動していない(`max_par` は最後まで 9)。
5. crash、failure ファイル、sha の不一致、Traceback、OOM は、どの腕でも起きていない。各腕とも 11/11 part が complete になり、終了時の sha 照合も通った。
